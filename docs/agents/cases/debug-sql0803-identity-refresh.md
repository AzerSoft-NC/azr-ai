| Commits phares | — (correctif DBA / SQL, pas de patch applicatif) |
| Période | 22 juillet 2026 |

## Contexte

Après un refresh de base INT avec des données prod,

 `VoletService.saisir` échoue en insert (`SQL0803` duplicate key). L’agent : 

- trace `upsertVolet` → `persist`
- Classe des hypothèses
- identifie une identity IBM i en retard sur `MAX(id)`
- guide la lecture du catalogue, 
- généralise à tout le schéma DEC 
- fournit un script SQL dynamique réutilisable.

### Tour 1 — agent

- Constat : insert neuf (`idVolet == null`) via `VoletRepository.upsertVolet` → `persist` sur `DEC_VOLET` (`GENERATED BY DEFAULT AS IDENTITY`) ; rejet **identity/PK** (`SQL0803`), pas validation métier.
- **Hypothèses classées :**
  1. **H1** identity `DEC_VOLET` désynchro (`NEXT` ≤ `MAX(ID_CES_VOLET)`) après import / refresh — *si vrai* : `ALTER … RESTART WITH max+1` débloque `saisir`
  2. **H2** unique index hors scripts repo (ex. contrainte système sur FK) — *si vrai* : nom contrainte ≠ `ID_CES_VOLET`
  3. **H3** identity RIB (`createNewRib`) — moins probable (stack sur persist volet, pas RIB)
  4. **H4** payload / FK déjà unique ailleurs — *si vrai* : SQL Hibernate montre une FK en collision
  5. **H5** double-saisie concurrente — improbable sans unique métier sur volet
- Checks demandés : `MAX(ID_CES_VOLET)` + lecture pointeur identity (catalogue IBM i).

## Ce que ça illustre

- **Hypothèses avant correctif** : le ranking H1–H5 rend le refresh ops décisif pour H1, pas un verdict unique magique.
- **Effet domino post-refresh** : volet OK ≠ schéma OK — enchaîner toutes les identities.
- **Script générique ≠ script exécutable partout** : catalogue `IS_IDENTITY` puis friction client SQL (delimiter) jusqu’au fallback littéral simple.
- **Outil = partie du diagnostic** : SQL0104 peut être DBeaver, pas IBM i.
